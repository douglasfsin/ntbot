1. Visão executiva / propósito do produto

NtBot é uma plataforma web multi-tenant de inteligência de trading (foco B3: WIN/WDO e commodities/FX como XAUUSD) que:

  1. Consolida contexto macro, market intelligence, market drivers e engines (Wyckoff, SMC, volume, confluence) num workspace unificado.
  2. Recebe market data via Connector Windows (Profit DDE/RTD/ProfitDLL, MT5 OHLCV) → NtBot.Api → SignalR / REST.
  3. Apresenta leituras em Blazor Interactive Server (NtBot.Web) com health, badges de macro e auth cookie/JWT.
  4. Oferece billing Stripe, mentor/coach, quant strategy e stubs de execução (grid, risk, positions).

Não é (ainda) um OMS completo de execução retail. É um sistema de leitura, confluência e sinalização — com pontes para MT5 / Profit / NinjaTrader onde configurado.

Produto visual principal: NtBot.Web (Blazor, tema dark Binance-like), rotas sob /app/*.

Produto irmão / referência de blueprint: Orbital / Dashboard Leilão RTD (DahsboardLeilaoRTD) — desktop MAUI + MarketData.API local; NtBot é a linha SaaS/web + connector.

6. Connector Windows — DDE / RTD / MT5

O NtBot.Connector.Windows é o edge local (máquina do operador/servidor Windows) que:

  1. Lê providers: Profit RTD, Profit DDE, ProfitDLL, MT5, NinjaTrader (conforme config).
  2. Normaliza em MarketTick / NormalizedMarketTick via MarketData bus.
  3. Publica para a API: REST /api/connector/* (incl. candles OHLCV) e SignalR /hubs/connector.

Princípios (ver docs/connector/architecture.md):

  • Nenhum consumer (Web, Quant, Macro) acessa Profit/MT5 diretamente.
  • Providers intercambiáveis via configuração.
  • OHLCV MT5: sync multi-timeframe (M5, M15, M30, H1) → PostgreSQL Candles.

Limite: ProfitChart RTD / interop nativo não roda em container Linux — depende do connector no Windows.

Módulo NtBot.TradingIntelligence — workspace unificado de leitura, confluência e sinalização (comparável a Bloomberg/Koyfin na versão NtBot).

8.3 Como é determinada a sinalização de força (compra / venda)

Fluxo resumido (orquestrado por TradingIntelligenceService.BuildSnapshotCoreAsync):

  1. Candles → engines de preço (Trend/SMC → Structure, Liquidity, Volume, Wyckoff, Volatility) + Macro + Correlação (MI + drivers).
  2. Cada engine produz Score 0–100, Confidence e BaseWeight.
  3. Peso efetivo = BaseWeight × Clamp(Confidence/100, 0.15, 1.0); Unknown → peso 0.
  4. Score de confluence = Round( Σ(Scoreᵢ × EffectiveWeightᵢ) / Σ(EffectiveWeightᵢ) ), clamp [0, 100]. Risk não entra na média direcional — só multiplica a confiança.
  5. ConfluenceClassification.ClassifyRecommendation(score) mapeia o número para a recommendation.
  6. Gates de confiança e anti-loss podem forçar AGUARDAR mesmo com score direcional.

8.3.1 Tabela de recommendation (sinal principal)

ScoreRecommendationBias típico

43 – 57NEUTROSideways

Mesmos limiares 58 / 42 definem bias por engine (BiasFromScore) e classificação de bias do score (ClassifyBias). Classification qualitativa do score (Classify): ≥95 Extrema, ≥85 Muito Alta, ≥70 Alta, ≥55 Moderada, ≥40 Neutra, ≥20 Fraca, senão Muito Fraca.

8.3.2 Resolução de Bias (chip na UI)

Prioridade em ConfluenceEngine.ResolveBias:

  1. Consenso multi-timeframe (sem conflito e AgreementPercent ≥ 60).
  2. Senão, bias da Structure (Trend/SMC) se Bullish/Bearish.
  3. Senão, maioria dos biases dos engines (±1 de margem).
  4. Senão, ClassifyBias(score).

8.4.1 Multi-timeframe (XAUUSD)

  • TFs típicos: 5, 15, 30, 60, 240, 1440.
  • Por TF: média (SMC + Wyckoff + Volume) / 3 → ≥58 bullish, ≤42 bearish.
  • Conflito MTF reduz confidence ×0,82; agreement ≥70% multiplica ×1,05 (cap 100).
  • Interseções de faixa de preço (pares 5×15, 5×30, …): HighConfluence se score ≥ 70 e overlapRatio ≥ 0,15 — aparecem como chips no gráfico.

8.6 Zonas operacionais (StrongBuy / ModerateBuy / …)

Faixas de preço tipadas geradas por OperationalZoneEngine.BuildZones (NtBot.TradingIntelligence/Engine/OperationalZoneEngine.cs), orquestradas em TradingIntelligenceService.BuildSnapshotCoreAsync depois do Confluence e das interseções multi-TF. Exibidas em OperationalZonesPanel e como overlays no TradingIntelligenceChart.

Não são o sinal principal. Dizem onde o preço pode reagir (demanda/oferta, liquidez, FVG). A recommendation (COMPRA/VENDA/NEUTRO) continua vindo só do Confluence + gates.

8.6.1 O que são

Cada zona é um OperationalZone:

CampoSignificado
TypeStrongBuy · ModerateBuy · Neutral · ModerateSell · StrongSell — cor da faixa na UI
LabelNome legível (ex. “FVG / Confluência 5x15”, “Demand / Order Block 60min”)
PriceLow / PriceHighBanda de preço da zona
ConfluenceScoreScore associado (interseção, TF ou confluence global) — usado no ranking
SourcesTags heurísticas (Wyckoff, SMC, Volume, FVG, Liquidez…)
TimeframePar de TF, TF único, multi, session ou target

8.6.2 Inputs (origem dos números)

InputComo é obtido no código
ConfluenceScoreResultScore / Bias / Recommendation do ConfluenceEngine (já com pesos e gates)
TimeframeAnalysis[]WyckoffScoreProvider.GetTimeframeAnalysesAsync: por TF, ~120 candles → High = max(High), Low = min(Low), Mid = (High+Low)/2; scores Wyckoff / SMC / Volume do engine no mesmo candle set
TFs analisadosChartTimeframes + ConsensusExtraTimeframes; XAUUSD força 5, 15, 30, 60, 240, 1440
TimeframeIntersection[]TimeframeIntersectionEngine.Calculate — overlap de ranges entre pares de TF (ver 8.6.3)

Não há volume profile real nem order book: POC, VWAP e “order block” são proxies heurísticos sobre High/Low/Mid e scores W/S/V.

8.6.3 Interseções multi-TF (pré-requisito das zonas FVG)

Pares avaliados: 5×15, 5×30, 5×60, 15×30, 15×60, 30×60.

overlapLow  = max(Low_A, Low_B)
overlapHigh = min(High_A, High_B)
se overlapHigh ≤ overlapLow → descartar

overlapRatio = (overlapHigh − overlapLow) / min(range_A, range_B)
se overlapRatio < 0,08 → descartar   // MinOverlapRatio

engineScore   = (W_A + W_B + S_A + S_B + V_A + V_B) / 6
alignmentBonus = +4 se ambos W≥65; +4 ambos S≥65; +2 ambos V≥65; −3 se ambos W≤35
overlapBonus  = Clamp(overlapRatio × 20, 0, 15)

score = Clamp(engineScore + alignmentBonus + overlapBonus, 0, 100)

HighConfluence ⇔ score ≥ 70 e overlapRatio ≥ 0,15

Só interseções com HighConfluence = true viram zona “FVG / Confluência {par}”.

8.8 Gates que forçam AGUARDAR

Mesmo com score de COMPRA/VENDA, a recommendation vira AGUARDAR (bias → Sideways) quando:

  1. Confiança Baixa ou Muito Baixa (ConfidenceLevels.BlocksDirectionalTrade): confidence < 45 → bloqueia direção.
  2. Anti-loss (AntiLossFilter): ≥ 2 motivos ou penalty ≥ 28 — exemplos de penalty: spread alto (XAUUSD default max 45 → +22), ATR% > 1,5 (+20), ranging (+14), conflito TF (+18), volume fraco (+12), structure indefinida (+16), sessão baixa liquidez UTC 21–07 no ouro (+10), calendário high-impact (+15).
  3. Qualquer BlockingFactors não vazio enquanto recommendation ainda contém COMPRA/VENDA.
  4. Dados insuficientes → AGUARDAR DADOS.

Níveis de confidence: ≥85 Institucional, ≥72 Muito Alta, ≥58 Alta, ≥45 Moderada, ≥30 Baixa, <30 Muito Baixa. Risk level (a partir da confidence): ≥80 Baixo, ≥60 Moderado, ≥40 Alto, senão Extremo.

10. Riscos e limites conhecidos

  1. RTD/DDE/ProfitDLL só no Windows — cloud Linux não substitui o connector local.
  2. Stubs de execução — risk/grid/positions/signals/trades ainda não são produto completo.
  3. Dependência de feeds — qualidade do TI depende de connector saudável + providers macro.
  4. n8n / Redis — insights IA e cache são opcionais; status exposto em /api/trading-intelligence/status.
  5. Multi-tenancy / billing — planos Stripe devem permanecer alinhados com claims de sessão.
  6. Latência Blazor Interactive Server — UI sensível a rede; hubs mitigam polling.
  7. Qualidade de drivers — variações anômalas (ex. Dollar Index −99% no painel) contaminam impacto/score de Drivers e o blend Correlação; validar feeds antes de operar o badge COMPRA/VENDA dos drivers.
